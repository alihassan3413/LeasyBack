## 5. Routes intentionally excluded

- **The unprefixed `/auth/*` alias** for the same 5 endpoints (registered in `bootstrap/app.php` for the legacy `leasyback_web` SPA) — same controller, same behavior as the `/api/auth/*` routes; documenting both would just duplicate every entry. Noted in the `#[Group]` description and in `AUTH_MODULE.md` §6 instead.
- **Inertia web session routes** (`routes/auth.php`: `/login`, `/register`, `/logout`, `/forgot-password`, etc.; `routes/settings.php`): these return redirects/Inertia responses, not a JSON API contract, so an OpenAPI/Postman representation doesn't fit them. Documented narratively in `AUTH_MODULE.md` §6 instead.
- **UserProfile, DekraProcess, B2B, Vehicle, Order, Workshop, Admin, Tim** and all other business-module routes — out of scope per the task; the `scribe.routes[0].match.prefixes` config is scoped to `api/auth/*` only, so nothing from these modules can be picked up even if they're added to `routes/api.php` later without a matching route pattern.

## 6. Authentication configuration

`config/scribe.php`:
- `auth.enabled = true`, `auth.default = true`, `auth.in = AuthIn::BEARER`, `auth.name = 'Authorization'` — matches the real mechanism (Sanctum bearer token via the `Authorization` header). No JWT terminology anywhere in the config or generated docs.
- `register` and `login` are marked `#[Unauthenticated]` on the controller — confirmed in the generated OpenAPI spec as `security: []` on those two paths only.
- `logout`, `me`, `changepassword` inherit the class-level default and show the global bearer `security` requirement (confirmed: no per-path override needed since they're already `auth:sanctum`-protected in the router).

## 10. Endpoint documentation gaps / known issues found (not fixed)

Per instructions, behavior was documented as-is rather than changed:

1. **`user_id` in API responses is the internal bigint `id`, not a public-safe identifier.** `register`, `login`, and `me` all return a `user_id` field whose value is `$user->id` directly. There is no separate UUID or other public identifier column on `User`. Documented explicitly in both `AUTH_MODULE.md` §3 and inline in the Scribe `#[Response]` descriptions for `register`/`me`.
2. **No `device_name` parameter on login.** Every successful login creates a Sanctum token literally named `'auth-token'` — there's no per-device naming or multi-session tracking. Documented in the login endpoint's response description.
3. **`UserType::Werkstatt`'s stored value is `'Werksatatt'`** (a typo relative to the enum case name) — left unmodified since changing a stored enum value is a data-affecting decision outside this task's scope; called out explicitly in `AUTH_MODULE.md` §4 so it isn't mistaken for a documentation typo.
4. **Login's 401 response is intentionally undifferentiated**: wrong password, unknown email, and a deactivated account all produce the exact same `401 "Invalid credentials."` body (no enumeration). Documented as a single response example with an explanatory description rather than three separate (and misleadingly distinct-looking) response examples.
5. **No automatic response calls.** Every endpoint either mutates state (register/login/logout) or requires real auth Scribe can't safely fabricate (`me`, `changepassword`) — see `config/scribe.php`'s `responses` strategy, which removes `ResponseCalls` entirely in favor of explicit `#[Response]` attributes reflecting actually-observed behavior. No real mail was queued, no real tokens were issued, and no permanent rows were created by the documentation-generation process itself.

## 11. How developers keep docs updated

See `AUTH_MODULE.md` §8 (checklist) and §10 (commands). In short: change the Form Request/controller, add or update the corresponding Scribe attributes, run `php artisan scribe:generate`, then `vendor/bin/pint --dirty --format agent` and `php artisan test`.

## 12. CI recommendation (not implemented — no CI exists in this repo)

No CI configuration exists anywhere in this repository, so none was added, per instructions. If CI is introduced later, `AUTH_MODULE.md` §12 documents the recommended checks: regenerate Scribe docs and diff against a checked-in reference copy of `openapi.yaml` (if one is committed for that purpose) to catch undocumented endpoint drift, then `php artisan test` and `vendor/bin/pint --test`.

## 13. Ready for team use?

**Yes, for the 5 documented auth API endpoints.** The generated HTML docs, OpenAPI spec, and Postman collection are complete, accurate to current behavior, and verified to load. Two caveats worth flagging to the team before wider rollout:
- The `--test`-mode whole-repo Pint failures (§9) are pre-existing and unrelated to auth, but will show up if anyone runs a repo-wide lint gate — worth a separate cleanup pass.
- The `user_id`/internal-bigint-exposure gap (§10.1) is now clearly documented, but is a product/security decision still open — see `docs/AUTH_PRODUCTION_IMPLEMENTATION_PLAN.md` §2 Decision 1 for the greenfield rationale, and revisit if a real external consumer ever needs a non-enumerable public identifier.
