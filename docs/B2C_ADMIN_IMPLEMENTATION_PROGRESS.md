## 3. Important decisions

- **`AdminController::orders()` fix = wire in `AdminQueryService`, not a fresh rewrite.** The plan explicitly calls this out (§4, Checkpoint 1) — the service already existed, already used Eloquent's query builder throughout (fully parameterized), and already allow-lists `order_status` before it reaches any query. The controller method is now three lines. `vehicles()`, `ordersByUser()`, `vehiclesByUser()`, `ordersByUserType()`, `vehiclesByUserType()` were **not** touched — they either already use `?` bindings for user-controlled values or (for the `*ByUserType` pair) are pre-existing stubs that just delegate to the now-fixed methods. Rewiring those too would have meant changing their response shape without being asked; left for whichever checkpoint actually builds the Admin listing UI.
- **New `OrderStatus`/`VehicleOwnerType` enums, not raw arrays.** Mirrors the existing `UserType` enum + `users_user_type_check` migration pattern already established in this codebase (see `database/migrations/2026_07_31_000002_...`). Same shape: enum → `values()` → Postgres CHECK constraint built from those values, so the constraint can't silently drift from the enum.
- **The "introduce the first concrete Policies" scope item was already satisfied before this checkpoint started.** `WorkshopPolicy`, `VehicleDocumentPolicy`, and `VehicleReportDocumentPolicy` were added in the prior session as part of the storage-architecture directive. This checkpoint's authorization work was therefore about **testing** those Policies (zero tests existed for any of them), not adding new ones — which matches this checkpoint's actual title, "Foundation Testing and Authorization."
- **Canonical vs. shim model classes matter for Policy type hints.** Several models live at `App\Modules\UserProfile\...\Models\X` with a thin re-export shim at `App\Models\X extends ...\X`. The three Policies type-hint the **shim** class (e.g. `App\Models\VehicleReportDocument`), matching how every real controller queries these models (`VehicleReportDocument::find()` via the shim import). One test (`VehicleReportDocumentPolicyTest::test_view_ability_requires_published_or_admin`) calls the Policy directly with no HTTP round-trip in between (no live route exercises the `view` ability yet), so it re-fetches through the shim class before asserting — otherwise PHP's type check rejects the canonical-class instance the factory produces. Every other new test goes through real HTTP routes, which already return shim instances naturally.
- **Factories for the four `App\Modules\...` models needed explicit `newFactory()` overrides.** Laravel's default factory-name resolver strips the app namespace and preserves the rest of the path (e.g. `App\Modules\UserProfile\Vehicle\Models\Vehicle` → `Database\Factories\Modules\UserProfile\Vehicle\Models\VehicleFactory`), not just the class basename. Discovered via a failing first test run; fixed by adding `protected static function newFactory()` to each affected model rather than moving/renaming factories.
- **Unauthorized vehicle-document access returns 404, not 403**, by existing design in `VehicleDocumentController` (deliberately doesn't reveal whether a vehicle/document exists to a caller without access). Tests assert `assertNotFound()` for the non-owner case there, and `assertForbidden()` everywhere else (Workshop, Admin routes), matching each controller's actual behavior rather than a single assumed convention.
- **Only the factories this checkpoint's tests actually need were added** (`Vehicle`, `Workshop`, `VehicleDocument`, `VehicleReportDocument`, `LeasybackOrder`) — not every domain model, per this checkpoint's explicit instruction to narrow that item from the master plan's broader "every model" framing.

### Checkpoint 2 decisions

- **The real IDOR fix is `ProfileService`'s ownership-scoped query, not the Policy.** `updateAddressContact`/`updatePreferences` accept a client-supplied `address_id`/`contact_id`/`preference_id` — there's no way to authorize "is this the caller's own resource" via a Policy instance check without first loading the record, and loading it correctly (scoped to `user_id`) *is* the fix. `ProfileService::updateAddressContact` joins `user_profiles` → `contacts` and requires `up.user_id = $user->id` before touching anything, `lockForUpdate()`'d, returning a clean 404 (not a silent no-op, not a 403) when the ids don't resolve to the caller's own profile. `ProfilePolicy` handles the orthogonal question of *who may create/update a profile at all* (see below) — the two layers are complementary, not redundant.
- **`ProfilePolicy` denies Admin on `create`/`update`, allows Admin on `view`**, per `docs/B2C_ADMIN_PERMISSION_MATRIX.md`'s explicit UserProfile row: "Admin has no legitimate use case to edit a customer's personal contact info directly." Since `createProfile`/`updateProfile`/`createPreferences`/`updatePreferences` don't need a loaded model instance to decide (the rule is purely user-type-based — instance-level ownership is `ProfileService`'s job, see above), they're authorized directly in each Form Request's `authorize()`, keeping the controller itself free of any explicit `$this->authorize()` calls.
- **One Policy class, two registered models, distinct ability names.** `LeasybackUserProfile` (profile/address/contact/phone bundle) and `UserPreference` are different Eloquent models but conceptually one "self-service profile" domain per this checkpoint's instructions, so both are registered against the same `ProfilePolicy` in `AuthServiceProvider`. Since one PHP method can't type-hint two different classes, the profile abilities are named `viewProfile`/`createProfile`/`updateProfile` and the preference ones `viewPreferences`/`createPreferences`/`updatePreferences`, rather than reusing `view`/`create`/`update` for both.
- **`viewProfile`/`viewPreferences` have no live route yet.** `ProfileController::show()` always resolves `$request->user()`'s own profile — there's no client-suppliable identifier, so there's no IDOR surface to authorize against today. The abilities exist and are tested directly (`ProfilePolicyTest`) because the permission matrix documents Admin-view-any as a legitimate future capability; wiring a real admin-view-by-id endpoint is not in this checkpoint's scope.
- **Invalid-identifier / validation-failure responses verified clean.** A malformed `address_id`/`contact_id` (not a UUID) is rejected by `AddressContactRequest`'s validation rules before the controller ever runs (422, standard Laravel validation-error shape). A well-formed but nonexistent or not-yours id reaches `ProfileService`, which throws `HttpResponseException` wrapping a plain `{"error": "..."}` JSON body — Laravel's exception handler renders `HttpResponseException` as-is regardless of `APP_DEBUG`, so no `exception`/`file`/`line`/`trace` keys leak even in this repo's `APP_DEBUG=true` default. Both cases have an explicit regression test asserting the response body has none of those debug keys.

### Checkpoint 3 decisions

- **Two separate auth mechanisms exist side by side, on purpose.** The `/userprofile/*` API routes (Checkpoint 2) are Sanctum-bearer-token-only — `bootstrap/app.php` has an explicit comment that cookie/CSRF middleware must never be applied to them, since the legacy `leasyback_web` SPA authenticates that way. The new Inertia pages instead use **new, separate, session-authenticated web controllers** (`Settings\AddressController`/`PreferencesController`, under the existing `auth`+`active` web middleware group) that call `ProfileService` directly — not the Sanctum API controller, and the Inertia frontend never touches a bearer token. Both entry points share the same `ProfileService` and the same `AddressContactRequest`/`PreferencesRequest`, so the IDOR fix and validation rules can't drift between them.
- **`ProfileService` reports domain errors (409 already-exists, 404 not-found) via `HttpResponseException` with a bare `{"error": "..."}` body** — correct for the JSON API, but Inertia doesn't know how to render a bare JSON body mid-visit. `HandlesServiceValidationErrors` (a small trait, not a rewrite of `ProfileService`) catches it in the two new web controllers and redirects back with the same message flashed into a named error-bag field (`address`/`preferences`), which Inertia's `useForm().errors` picks up exactly like a normal validation error. `ProfileService` itself is untouched by this — the translation happens only at the web-controller boundary.
- **Added `ProfileService::findPreferencesForUser()` instead of reusing `findForUser()`.** `findForUser()` returns `null` for the *entire* bundle whenever no `user_profiles` row exists — but `user_preferences` is a fully independent table a user could populate without ever creating an address/contact profile. Reusing `findForUser()` for the Preferences page would have silently hidden real preferences data for that (real, schema-permitted) case. Caught during design, not during a failing test — `test_preferences_are_visible_even_without_an_address_profile` locks it in as a regression test now that the fix exists.
- **Address & contact merged into one page/one card, not two**, unlike the legacy `leasyback_web`'s separate `AccountDetail` (address + identity) and `ContactPerson` (a distinct secondary contact person) components. The current Laravel schema only has one `contacts` row per profile (`user_profiles.contact_id`, 1:1) — there's no second "contact person" concept to port. Presenting them as one form matches the actual backend resource (`POST/PUT /userprofile/address-contact` is already one combined endpoint) rather than inventing a two-contact model that doesn't exist.
- **The reusable dropdown is genuinely non-native, per the explicit instruction.** `ui/select/*` wraps `reka-ui`'s `SelectRoot`/`SelectTrigger`/`SelectContent`/`SelectItem` (the same headless-UI foundation already used for `Button`/`Checkbox`/`Label`/`DropdownMenu` in this repo), ported from the legacy `leasyback_web` repo's own `ui/select/` (which already existed there, unused by its forms) and re-styled to match this repo's Tailwind tokens. The one pre-existing dropdown-like thing in this repo, `Register.vue`'s plain `<select>` with a manual `ChevronDown` overlay, was left as-is (out of scope, not part of this checkpoint) rather than retrofitted.
- **`SelectField.vue` is the actual reusable unit, not the five `ui/select/*` primitives individually.** Composing `Select`+`SelectTrigger`+`SelectValue`+`SelectContent`+`SelectItem` by hand in every page would defeat the point of "reusable" — `SelectField` takes a flat `modelValue`/`options`/`placeholder` API (matching every other form field in this codebase) and is what `Address.vue`, `Preferences.vue`, and `PhoneNumberFieldset.vue` actually import. It's reused **four times** across salutation, country, language, and timezone (plus the phone-prefix field), not built once and used once.
- **No live browser verification was possible.** `mcp__claude-in-chrome` reported the extension not connected in this environment. Correctness was checked instead via `npm run build` (Vue/TS compiles), `npm run lint` (eslint, clean), and Feature tests that assert exact Inertia prop values (`assertInertia(...->where(...))`) over real HTTP requests through the full middleware/controller/service stack — this proves the data flow end-to-end but does **not** confirm the dropdown opens/closes correctly, keyboard nav works, or the visual layout is right. Whoever reviews this should click through `/settings/address` and `/settings/preferences` at least once before considering Checkpoint 3 fully done.
- **`vue-tsc --noEmit` doesn't run cleanly in this repo** (pre-existing `tsconfig.json` issue — its `"types"` array includes a relative path, `./resources/js/types`, which isn't a valid `types` entry for a direct CLI invocation, independent of anything in this checkpoint). Confirmed pre-existing by the fact that it fails identically on `vue/tsx`, one of the untouched default entries. Not fixed (out of scope, config surface not directory this checkpoint owns) — `npm run build`/`npm run lint` remain the real gates, as they're what the project's own scripts define.

### Checkpoint 4 decisions

- **`findByOwner`'s fix ignores the client-supplied `ownerId` for the actual access decision, but still checks it.** The correct authorization question is "does the authenticated user have access to *this* vehicle at all" — answered entirely by `VehicleScopeService::findVehicleWithAccess($vehicleId, $user)`, which never looks at `$ownerId`. Once that resolves a vehicle, the code cross-checks the vehicle's *real* owner against the requested `$ownerId` purely to preserve the endpoint's existing "id + owner must both match" response contract (a caller who gets the pairing wrong still gets 404, same as before) — not as a security boundary. This avoids two smaller mistakes: trusting `ownerId` as an access grant (the original bug) or dropping it from the response contract entirely (an unrelated, unrequested behavior change).
- **`update()`/`assignProfile()` were refactored to use the Policy even though they weren't vulnerable.** They already called `VehicleScopeService::findVehicleWithAccess` directly and were already correctly scoped — this wasn't a fix, it's what "formalize `VehiclePolicy` on top of the already-good `VehicleScopeService`" (the plan's literal Checkpoint 4 wording) means in practice: make the Policy the actual mechanism controllers use, not just a class that exists in isolation. The 404-not-403 response shape was preserved exactly (`! $vehicle || ! $user->can('update', $vehicle)` still returns the identical message either way) so this is a pure internal refactor, not a behavior change.
- **The Vehicle-document Policy regression-test item needed no new code.** `VehicleDocumentPolicyTest` (added in Checkpoint 1) already proves owner/non-owner/admin access on list/view/delete. Re-verified by re-reading it and confirming it still passes; no duplicate test was added. Consistent with how Checkpoint 1 handled the already-satisfied "introduce Policies" item — check what already exists before assuming a plan bullet means new code.
- **20 MB → 10 MB is a real spec-compliance fix, not a guess.** `docs/B2C_ADMIN_MIGRATION_AUDIT.md` explicitly documents the reference (Rust) system's cap as 10 MB and frames Checkpoint 4's job as verifying "Laravel enforces the same cap" — finding it set to 20 MB and leaving it as "verified, but wrong" would defeat the point of the checkpoint. The mime allow-list itself (`pdf,jpg,jpeg,png`) already matched and needed no change; Laravel's `mimes` rule also sniffs actual file content rather than trusting the extension/declared content-type alone, which is stricter than the documented reference behavior — noted in the controller comment, not changed (already an improvement, nothing to fix).
- **Vehicle creation (`store()`) and the two "*ByUserType"/`dashboard`/`listByOwner` methods were left untouched.** `store()`'s Admin/Firmenkunde/Privatkunde branching decides who the *new* vehicle's owner becomes — that's business logic, not an access-control gate, and isn't flagged anywhere as vulnerable. `listByOwner()`/`dashboard()` already have correct (if inline, duplicated) ownership checks and aren't broken; consolidating them through `VehicleScopeService::resolveOwnerId()` would be a reasonable future cleanup but isn't what this checkpoint's four explicit bullet points asked for, so it was left alone to keep the diff reviewable.

### Checkpoint 5 decisions

- **`store()`/`update()`/document upload/delete were extracted into `VehicleService`, not just duplicated into the new web controller.** Checkpoint 4 already extracted `findByOwner`'s scoping logic into a Policy; this checkpoint needed the *mutation* logic (owner resolution, audit logging, document storage) available from a second, non-Sanctum entry point. Rather than copy-pasting the Sanctum API controller's bodies into the new web controller (which would let the two drift out of sync over time, the exact anti-pattern Checkpoints 2–3 fixed for Profile), both the API and web controllers now call the same `VehicleService` methods. The API controllers shrank as a side effect — a deliberate, not incidental, part of "keep controllers thin."
- **Found `VehicleService::listVehiclesWithOrders()` was stale (referenced a column Checkpoint 0 renamed, hardcoded the wrong disk) because it was still unused code.** Since this checkpoint is the method's first real caller, fixing those two bugs before activating it was necessary, not optional — shipping a "wire in the existing service" change while knowingly leaving it broken would defeat the purpose. Deliberately did **not** touch the Sanctum API's own `dashboard()` method (which has its own, still-separate, still-working inline implementation) to wire it through the now-fixed service too: `listVehiclesWithOrders()`'s response shape genuinely differs (missing `b2b_id`/`b2c_user_id`/`assigned_profile_id`, differently-shaped `status_updates`/`order_confirmations`) from what `dashboard()` currently returns, and that's a live endpoint the legacy `leasyback_web` SPA calls — changing its response shape wasn't asked for and wasn't risked. `dashboard()` and `listVehiclesWithOrders()` remain two independent implementations of a similar query on purpose, for now; consolidating them is listed under deferred work.
- **The "unbekannt" checkboxes are ported as UX, not as a data-integrity workaround.** The legacy Add-Vehicle modal sent a fake "today" placeholder for `leasing_end_date` (and `first_registration_date`, which isn't even shown as a field in this rebuild) because *its* backend required those fields non-null. This Laravel backend's `StoreVehicleRequest`/`UpdateVehicleRequest` already validate both as `nullable`, so the new modal sends real `null` when "Ich weiß es nicht" is checked — preserving the useful UX pattern (an explicit, honest "I don't know" affordance) without importing the data-quality problem (a fabricated leasing-end date that looks real) that the workaround existed to paper over in the old system.
- **The duplicate-document-type "replace" flow moved entirely to the client.** The legacy backend rejected a same-`document_type` re-upload with an "already exists" error, and the old UI's replace-flow was built around catching that error. This backend's `VehicleDocumentController::upload()` has never done that check — it always creates a new row. Rather than add a new backend rejection (a real behavior change to an existing, tested, working endpoint, and out of this checkpoint's frontend scope) or drop the UX entirely, `UploadDocumentModal.vue` compares the selected type against the vehicle's already-loaded `documents` prop *before* submitting, and shows the identical inline warning/Replace/Cancel UI the legacy version did — same user-facing behavior, different mechanism.
- **No live browser verification, again.** Same `mcp__claude-in-chrome` "extension not connected" result as Checkpoint 3, re-checked at the start of this checkpoint's frontend work in case it had become available — it hadn't. The two new modals in particular (drag-and-drop, the reka-ui Select's keyboard/pointer interactions, the plate input's per-segment live validation) are exactly the kind of thing only a real browser check catches; flagged again under deferred work rather than silently assumed correct.
- **Row-level order-timeline expansion was not ported.** The legacy `VehicleTable`/`VehicleRow` had an expandable per-vehicle detail panel showing the full order timeline, inspection appointment, and driver contact info. That's genuinely order-domain UI (it's built from `order.request_payload`/`status_updates`, not vehicle fields), and the plan's own checkpoint sequence puts order-domain work in Checkpoints 6–7 (Order backend/frontend) — building a real version of it now, ahead of the Order backend checkpoint's own hardening work (the plan flags `TransitionOrderStatus` and an Offer BOLA fix as still-open there), would mean building UI against order data/endpoints that haven't been through the same audit-and-fix pass the Vehicle domain just got. The table still shows each vehicle's current status via the badge; the deep-dive panel is deferred, not silently dropped.

### Checkpoint 6 decisions

- **Only new endpoint-level admin transitions come in Checkpoint 11, not this one.** The status matrix's recommended table covers the *entire* lifecycle (through `inspected`/`workshop`/`reinspection`/`reworkshop`/`delivered`), but the plan explicitly assigns "Admin order list/detail, ... status transitions via the same `TransitionOrderStatus` action" to Checkpoint 11 ("Admin order management"). So `TransitionOrderStatus` enforces the *full* table now (ready for Checkpoint 11 to consume), but this checkpoint only wires it into the four endpoints that *already* touched `order_status` (`confirm`, `status`, `approve`, `confirmOther`) — it does not add new HTTP endpoints for the manual `confirmed → inspected → workshop → ...` progression. "Tests for every transition" is satisfied by calling the action directly (`tests/Feature/Order/TransitionOrderStatusTest.php`), not through new controller routes.
- **`reworkshop` has no forward transition beyond `cancelled`, deliberately, because the status matrix itself doesn't resolve this.** Open question #1 in `docs/B2C_ADMIN_STATUS_MATRIX.md` §1 explicitly asks whether `reworkshop` loops back to `reinspection` and says this isn't evidenced anywhere in the reference system — "confirm the real cycle with product." Inventing an answer (e.g. assuming a loop) would mean shipping unconfirmed business logic as if it were settled. `TransitionOrderStatus::ALLOWED_TRANSITIONS['reworkshop']` is `['cancelled']` only; a test (`test_undocumented_transitions_are_rejected`) locks in that `reworkshop → reinspection` and `reworkshop → delivered` are both currently rejected, so this is a visible, deliberate gap rather than a silent one. Revisit once product answers the open question.
- **The webhook API key finding is the same shape of bug as Checkpoint 4's 20 MB/10 MB mismatch: "already in config" isn't the same as "actually safe."** The checkpoint's literal instruction was "move the key to config if it isn't already" — a shallow read would have stopped at "it's already in `config('services.tuvsud.api_key')`, done." Actually checking the value showed a hardcoded fallback secret. Fixed the config *and* added defense in depth (fail-closed middleware, `hash_equals()`) rather than just deleting the fallback and trusting `.env` to always be configured correctly in every environment.
- **`approve()` keeps its own pre-check via `TransitionOrderStatus::allowedNextStatuses()` before calling the action for real.** The action's own lock-and-check would reject an already-approved order too, but only *after* the controller has already made a real, possibly-billed external HTTP call to TÜV SÜD. Checking `in_array('order_placed', TransitionOrderStatus::allowedNextStatuses($order->order_status))` first (unlocked, advisory) avoids that wasted call in the common case; the guarded, locked check inside the action is still the actual enforcement point, so a race between the pre-check and the real transition just means an occasional wasted external call, never an invalid status write.
- **`OrderPolicy`'s `approve`/`confirm`/`manageStatus`/`createStation` are all identical logic (`$user->isAdmin()`) but kept as distinctly named abilities**, matching the status matrix's own per-action "Actor" column and following the same precedent as `ProfilePolicy`'s several identically-admin-denying-but-distinctly-named abilities in Checkpoint 2. `manageStatus` exists now for Checkpoint 11 to use even though nothing calls it yet.
- **Controller error-response shapes were preserved exactly where they already existed**, even though every status-changing method now goes through `TransitionOrderStatus`. `approve()`'s original `400` with `{"error": "...", "current_status": ...}` is reconstructed in a `catch (ValidationException)` block rather than replaced with a generic 422, and non-admin checks still return `{"error": "..."}` (not Laravel's default `abort()` JSON shape) — this is backend work on live, already-integrated endpoints (the legacy `leasyback_web` SPA calls all of these), so response-shape stability mattered here the same way it did for `findByOwner` in Checkpoint 4.

### Checkpoint 7 decisions

- **Provider is derived from the chosen station, never a separate form field.** Surveyed `leasyback_web`'s `OrderCreationModal.vue` before building the new one: the customer only ever picks a station; the frontend maps `provider === 'dekra' ? 'others' : provider` to choose which create endpoint to call. The new web `OrderController::store()` reproduces the same rule server-side (look up the station, branch on `station->provider === 'tuvsud'`) rather than asking the frontend to choose a URL/provider itself — one call to `orders.store`, one station picker, matching the legacy UX without porting its per-provider endpoint-selection logic into the client.
- **The fee-acknowledgement gate is folded into `OrderCreationModal.vue` itself, not a second dialog.** The legacy frontend has a separate `OrderFeeConfirmModal.vue` shown only after "Bestätigen" is clicked in the main form. Nothing about the fee notice needs its own dialog lifecycle — a required checkbox inside the same form, gating the submit button (`canSubmit` requires `fee_acknowledged`), reproduces the same "you must acknowledge before booking" UX with one modal instead of two. The acknowledgement is a client-side UX gate only, not persisted — the legacy backend never stored it either (the `fee: 200` warning text is purely informational, unconnected to any DB column in either system).
- **Order creation's date/time picker is native `<input type="date">`/`<input type="time">`, not a ported `CalendarDateField`/`TimePicker`.** The legacy pickers add weekend-blocking and a bespoke calendar UI on top of a plain date; this checkpoint keeps only the one constraint that's actually load-bearing (a `min` a few days out, so a booking can't be made for today/tomorrow), skipping the weekend/holiday logic as unnecessary complexity for a first pass. Cascading Bundesland→Ort→Station filters and live Nominatim geocoding (also in the legacy modal) were not ported at all — this repo has no map library, and the flat `SelectField` station list (all providers, labelled with name/city/provider) is sufficient at the station counts this domain actually has.
- **The order-status timeline is a simplified 6-stage linear happy path, not a literal rendering of the status matrix's full graph.** `docs/B2C_ADMIN_STATUS_MATRIX.md` §1 documents open questions about whether `reinspection`↔`reworkshop` actually loops — building a timeline widget that visually implies a settled answer to an explicitly-unresolved product question would be worse than simplifying. `lib/orderFlow.ts` collapses `order_requested`/`order_placed` into one "Gebucht" dot (a Firmenkunde order visits both; a Privatkunde order skips straight to the second) and `reworkshop` into the same dot as `workshop`, rather than inventing a 10-dot timeline that implies more certainty about the cycle than the domain doc actually has. `cancelled`/`discarded` render as a single terminal badge instead of a partially-filled timeline, since there's no meaningful "how far did it get" position to highlight for either.
- **`OffersCard.vue` trusts `VehicleService::listVehiclesWithOrders()`'s existing offer filter, doesn't re-filter client-side.** The service already excludes `draft`/`cancelled` offers (matching `OfferController::customerList()`'s own rule) before they ever reach the Inertia response, so the component only branches on `published` (show the button) vs. `selected` (show an "Angenommen" badge instead) — it never needs to reason about statuses it will never receive.
- **Found the B2B vehicle-order test fixture needed a real `B2B` row, not a fake UUID.** `Vehicle::factory()->forB2b($uuid)` writes straight to the FK-constrained `vehicles.b2b_id` column — a `fake()->uuid()` with no matching `b2b` row fails the constraint at insert time (this only surfaces once a test actually exercises the Firmenkunde order path, which nothing had before this checkpoint). Fixed by creating a real `B2B::create()` backed by real `Contact`/`Address` factory rows (both already existed from Checkpoint 2/3, just not yet composed together) instead of adding a `B2B` factory — the model wasn't otherwise in this checkpoint's scope, and the two-line inline setup was cheaper than introducing a third new factory for one test.
- **No live browser verification, again.** Same limitation as Checkpoints 3 and 5 — flagged rather than silently assumed correct. The order-creation modal's date/time inputs, the SelectField station picker, and the expandable Dashboard row toggle are exactly the kind of thing only a real click-through catches.

### Checkpoint 8 decisions

- **`AdminPolicy` is registered as four named Gates, not `Gate::policy()`.** Every other Policy in this codebase binds to a real Eloquent model (`Vehicle`, `LeasybackOrder`, ...); the Admin operational actions this checkpoint centralizes (dashboard stats, cross-customer listings, a B2C/B2B status toggle, TIM sync) don't share one natural model — `deactivateCustomer`/`reactivateCustomer` alone would need to bind to *either* `User` or `B2B` depending on which endpoint, and `viewDashboardSummary`/`viewAny` aren't about any single resource at all. Rather than invent a marker class purely to satisfy `Gate::policy()`'s API (the kind of fake-model anti-pattern the plan explicitly warns against for Admin), each ability is registered individually via `Gate::define('ability', [AdminPolicy::class, 'method'])`. `AdminPolicy` itself still exists as a real, testable class — just registered differently.
- **Ability names were deliberately kept specific (`viewDashboardSummary`, not `viewAny`) to avoid a silent collision.** A raw `Gate::define('viewAny', ...)` would take priority over *every* model Policy's own `viewAny` method for any `$user->can('viewAny', SomeModel::class)` call anywhere in the app — Laravel checks raw gate definitions before resolving a model-specific Policy. `OfferPolicy` already has its own, different `viewAny`; a same-named plain gate would have silently overridden it. Verified this wasn't just theoretical by keeping the four new names unambiguous rather than trusting it wouldn't come up.
- **Kept four distinctly-named, identically-implemented abilities rather than one blanket `isAdmin` gate**, following the exact precedent Checkpoint 6 set for `OrderPolicy::approve/confirm/manageStatus/createStation` — matches `docs/B2C_ADMIN_PERMISSION_MATRIX.md`'s "Admin operational resources" table rows, and leaves room for any one of the four to later gain real per-action logic without touching the other three or every call site.
- **Did not use a `Gate::before()` hook that blanket-allows admins on any ability**, even though the plan text offers that as one of the two valid mechanisms. `OfferPolicy::select` explicitly returns `false` for Admin ("Admin must never be able to select as the customer" — a deliberate rule from the permission matrix, tested in `OfferPolicyTest`). A `Gate::before` returning `true` whenever `$user->isAdmin()` would short-circuit *every* ability check before any Policy method runs, silently reopening that exact hole. Named, scoped Gates avoid the risk entirely.
- **`EnsuresAdmin` was rewritten in place, not replaced with a new trait.** It already existed (found unused, in the Admin module's own `Support` namespace, with almost the right shape) — the same "existing-but-unused, wire it in" situation as `ProfileService`/`AdminQueryService`/`VehicleService::listVehiclesWithOrders()` in earlier checkpoints. Its old `adminDenial()`/`adminId()` methods hardcoded the `isAdmin()` check directly and were never called anywhere; replaced with one method that delegates to the new Gate and keeps every call site's exact existing error message, so refactoring the *mechanism* didn't change any *response body* on a live, already-integrated endpoint set (both `leasyback_web`'s admin panel and this checkpoint's own new tests exercise the real HTTP responses, not just the ability check in isolation).
- **`OfferController`'s reversed `customerList()` check (`user_type === 'Admin'` → excluded, not required) was left untouched.** It's structurally different from the ~20 checks this checkpoint targets — those all gate "Admin only," this one gates "everyone except Admin" — and `OfferPolicy` has no ability shaped like "must not be Admin." Forcing it into the same pattern would mean inventing a Policy method for a single call site with no other consumer; left as-is, matching the decision precedent of not fixing things that don't fit the pattern cleanly (Checkpoint 7's treatment of the same controller's `customerList`).
- **The Admin Inertia layout ships with exactly one real page (Dashboard), not stubs for Kunden/Fahrzeuge/Aufträge.** The plan explicitly assigns those three to Checkpoints 9/10/11; building placeholder pages for them now would mean either fake data (the exact "Systemstatus health card" anti-pattern the plan calls out by name) or empty shells nobody asked for. Shown as disabled sidebar items instead — visible information architecture, honest about what's not built yet, no broken links and no fabricated content.
- **Found and fixed two bugs unrelated to Admin auth itself, both discovered only because this checkpoint's own work touched the same files/query paths:** `NavMain.vue`'s `item.url`/`.href` mismatch (caught while building `AdminSidebar.vue` on the same `NavMain` component — would have silently reproduced the same broken-link bug in the new Admin nav if left alone) and `AdminController`'s Postgres-only `NOW()` in raw SQL (caught only because this checkpoint wrote the first-ever regression test for `updateB2cStatus`'s admin-succeeds path, which this repo's sqlite test database can't execute `NOW()` against). Both are the same shape of finding as Checkpoint 7's B2B factory FK issue: previously-unexercised code paths that nothing had ever actually called under test.

### Checkpoint 9 decisions

- **The customer detail view is a real routed page (`/admin/customers/{type}/{id}`), not the modal `leasyback_web`'s `UserDetail.vue` uses.** Surveyed the legacy component first: it's a Teleported modal with its own independent tab/loading state, triggered by a table-row click, never a URL. This app's own established convention is the opposite — every substantial content view so far (Settings pages, the Vehicle dashboard, the Admin dashboard itself) is a dedicated Inertia page, not a modal, and a modal here would mean the detail view can't be bookmarked, linked from elsewhere, or reached via browser back/forward. Deliberately deviated from the legacy's exact mechanism while keeping its actual *content* (header, address/meta, Fahrzeuge/Aufträge tabs) equivalent.
- **Activate/deactivate is new functionality with no legacy precedent — confirmed, not assumed.** The survey of `leasyback_web`'s `UsersView.vue`/`admin-users.api.ts` found status shown only as a read-only badge; no PATCH call exists anywhere in the legacy admin panel. Built anyway because it's explicit, itemized Checkpoint 9 scope in the plan, backed by endpoints (`updateB2cStatus`/`updateB2bStatus`) that already existed and were already tested from Checkpoint 8 — this checkpoint only needed to expose them through the UI. Added an inline confirm step before the actual toggle (matching `UploadDocumentModal.vue`'s established inline-confirm pattern from Checkpoint 5, not a new `ui/alert-dialog` primitive) since deactivating a customer is exactly the kind of action worth a confirmation, even without a legacy precedent to point to.
- **Server-side search, not a port of the legacy's client-side-search-over-everything.** `leasyback_web`'s `UsersView.vue` fetches the *entire* B2C or B2B list in 100-row chunks and searches/filters/paginates entirely in the browser — flagged by the survey itself as worth not repeating. `AdminQueryService::applyCustomerSearch()` adds one bound `LIKE` clause across a small allow-listed column set (never raw string interpolation — same discipline as the Checkpoint 1 SQL-injection fix), reusing the existing `page`/`limit`/`is_active` query-building rather than fetching everything.
- **The sidebar reskin uses scoped CSS-variable overrides on the existing `ui/sidebar` primitives, not a bespoke rewrite.** `Sidebar.vue`'s actual background class (`bg-sidebar`) lives on an inner node with no prop path to override directly, and the primitive's active/hover states are driven by `--sidebar-accent`/`--sidebar-accent-foreground` (Tailwind v4's `@theme inline` mechanism resolves these at paint time, the same mechanism this repo's own light/dark mode already relies on — confirmed, not assumed, since the dark-mode block in `app.css` depends on exactly this runtime-cascade behavior). `AdminSidebar.vue`'s scoped `:deep([data-sidebar='sidebar'])` block overrides only `--sidebar-foreground`/`--sidebar-accent`/`--sidebar-accent-foreground` plus the gradient background, entirely within its own component scope — the shared `ui/sidebar/*` components, `AppSidebar.vue` (B2C), collapse/expand behavior, and the mobile drawer are all completely untouched.
- **Deliberately did not chase two cosmetic details from the legacy sidebar**: (1) hover and active states share one accent color here (`hover:bg-sidebar-accent` and `data-[active=true]:bg-sidebar-accent` are the literal same CSS variable in the underlying component), where the legacy distinguishes hover (white/7% overlay) from active (solid green) — reproducing that distinction would mean forking the shared button-variant classes for Admin only, disproportionate to a hover-state nuance; (2) the legacy's floating collapse-toggle pill (white circle, custom border) wasn't reproduced — `AppSidebarHeader`'s existing `SidebarTrigger` (shared infra, already used by the B2C sidebar) does the same job. Both are visible if compared pixel-for-pixel side by side with the legacy; neither affects the nav structure or the primary brand colors, which were the explicit ask.
- **`applyOwnerFilter()` gained a `$b2bId` param instead of "borrowing" a company member's user id.** The Admin customer detail page knows a B2B company's `b2b_id` directly but not any one specific member's user id (and a company could in principle have zero members). Passing any arbitrary member's id into the existing `$userId` path would *work* (vehicle ownership is keyed by `v.b2b_id`, not the specific member), but is an indirect, easy-to-misread mechanism for a future reader. A direct `$b2bId` filter (`v.b2b_id = ?`) is explicit about what it means and doesn't depend on the company having at least one member.
- **`b2bList()` still returns one row per (user, company) membership, matching the untouched original query — this is now visibly a pre-existing quirk, not fixed.** A company with 3 members appears 3 times in the B2B customer list (each row showing the same company info alongside a different member). Not part of this checkpoint's explicit scope (the plan calls out the IDOR/role bugs and the list+detail+activate UI, not this), and changing it would alter a response shape the Sanctum API's live consumer wasn't asked to have changed. Flagged here and in deferred work rather than silently left for a future session to rediscover.
- **`B2BRequest` (found unused, matching `B2BService`'s exact expected shape) was wired into `store()`/`update()` alongside the IDOR/role fixes**, even though only `showByUser()`/`update()`'s *authorization* were flagged as buggy — `store()`'s own inline validation was looser (no required phone fields) than what `B2BService::create()`'s `insertContact()`/`replacePhones()` actually need, and having a controller-side FormRequest whose shape doesn't match its service's real requirements is exactly the kind of drift this session's "wire in the existing-but-unused thing" pattern exists to prevent.

### Checkpoint 10 decisions

- **"Create on behalf of a customer" lives on the customer detail page, not the vehicle list page.** The plan bullet is "Admin vehicle list/detail/create-on-behalf-of-customer" without specifying where the create action should be triggered from. Building it on the vehicle list would require an owner-search picker (find the right B2C user or B2B company by name/email) that doesn't exist anywhere in this app yet — real, non-trivial UI work. Building it on the customer detail page instead means the owner is already fully known from page context (`type`/`customer` props), so `CreateVehicleModal.vue` never exposes owner fields to the admin at all — it derives `vehicle_belongs`/`b2b_id`/`b2c_user_id` internally and the backend's own `StoreVehicleRequest` validation (this checkpoint's own hardening) still verifies them independently. Matches `leasyback_web`'s own precedent too, loosely — its `AdminAddVehicleModal.vue` was a per-customer-row quick action on the customer list, not a standalone vehicle-list flow.
- **`VehicleReportController`'s web counterpart exposes upload/publish/delete but not transfer.** `transfer()` copies an already-synced TIM assessment document by id — the admin needs to pick *which* assessment document to transfer, and there is no TIM-assessment-browsing UI anywhere in this app (TIM integration hardening is explicitly Checkpoint 12 territory per the plan). Building a transfer route with no UI to call it would be dead code; the Sanctum API's `transfer()` endpoint is untouched and still fully functional for whatever external/manual process already uses it. Revisit once a real TIM assessment browsing page exists to hook a picker into.
- **`enrichVehicles()` now attaches `report_documents` to every order-history entry, in the list response as well as the detail response** — a deliberate, accepted inefficiency. `vehicles()` (the list) doesn't need per-order report documents, but reusing the *same* enrichment method for both `vehicles()` and the new `vehicleDetail()` was worth a bounded extra query cost (documents per order, typically few) rather than forking `enrichVehicles()` into list/detail variants that could drift apart. Revisit only if the vehicle list page's payload size becomes an actual measured problem.
- **Two real, silently-corrupted-data bugs were found and fixed, not worked around.** `enrichVehicles()`'s `vehicle_documents` query and `reportDocuments()`'s signed-URL generation both still referenced `s3_key`, a column renamed to `path` by an earlier migration (`2026_08_01_000001_generalize_document_storage_columns`) — and SQLite's leniency toward unknown-identifier-as-string-literal meant neither one *errored*, they just silently returned garbage (`"s3_key"` as a fake document path; `null` as every report document's signed URL, swallowed by `temporaryUrl()`'s try/catch). Both were only surfaced because this checkpoint is the first to actually render this data on any page — confirmed via a scratch test dumping the real Inertia props before writing the permanent regression tests, not assumed from reading the code alone.
- **The route-name collision (`admin.vehicles.index` claimed by both a pre-existing Sanctum route and this checkpoint's new web route) was fixed by renaming the *API* route, not the new web route.** The API route's name is a purely internal Laravel construct — nothing calls it via `route()` anywhere (confirmed by grep before touching it), so renaming it changes zero external behavior, while the web route's name is actively used throughout the new Vue pages via `route('admin.vehicles.index')` and is the more natural name for a page users navigate to repeatedly. This is a generalizable risk for any future checkpoint (Checkpoint 11 will need `admin.orders.*` — the API already has `orders.index`/`orders.by-user-type`/`orders.by-user` under the same `admin.` prefix); flagged in the handoff notes below.

### Checkpoint 11 decisions

- **`discarded` (the reject action) got no endpoint, on purpose.** The plan's own Checkpoint 11 bullet says "approve/reject (confirm reject is wanted first, §13)" — an explicitly unresolved product question, not a settled requirement. `TransitionOrderStatus` already enforces `order_requested → discarded` (built in Checkpoint 6, ready for whenever this is confirmed), but no controller calls it: `AdminQueryService::orderDetail()`'s `available_transitions` filters it out before it ever reaches the frontend, and `Admin\OrderController::updateStatus()` independently excludes it from the `in:` validation rule too — defense in depth, not just a hidden button, so a direct API call can't exercise it either. Same treatment as Checkpoint 6's `reworkshop`-doesn't-loop gap: implement only what's actually specified, make the gap visible, don't guess an answer to an open question.
- **`order_placed` is excluded from `updateStatus()` for a different reason than `discarded` — it's not unconfirmed, it's just the wrong endpoint.** Transitioning to `order_placed` means firing a real, possibly-billed external TÜV SÜD HTTP call (`OrderService::approveOrder()`), which the generic manual-progression endpoint has no business doing implicitly via a status string. `approve()` is the only path to `order_placed`, keeping "this transition has side effects beyond a DB write" visible at the routing layer rather than buried in a conditional inside `updateStatus()`.
- **Extracting `OrderService::approveOrder()` surfaced a real class-identity bug, not just a refactor.** `OrderService.php` imported the `App\Models\LeasybackOrder` shim (matching `createTuvsudOrder()`/`createOtherOrder()`'s existing `LeasybackOrder::create()` calls, which work fine either way since they construct their own instance). But `TransitionOrderStatus::__invoke()` internally re-fetches the row through its own canonical-class import and returns *that* instance — so a method that both receives and returns "`LeasybackOrder`" via the shim-typed import produced a real `TypeError` under PHP's strict return-type enforcement the moment it returned whatever `TransitionOrderStatus` gave back. Fixed by switching `OrderService.php`'s import to the canonical class outright (structurally identical to the shim, no behavior change) rather than special-casing one method — the same "canonical vs. shim model classes matter for type hints" class of bug the Checkpoint 1 decisions section already flagged for Policies, now confirmed to bite Actions/Services too. Caught immediately by this checkpoint's own tests (a 500 on the very first `approve()` test run), not discovered later.
- **No explicit `$user->can(...)` calls in the new web `Admin\OrderController`/`OfferController`**, even though `OrderPolicy::approve`/`manageStatus` and `OfferPolicy::create`/`publish`/`cancel` all exist and are still used by the Sanctum API controllers. `routes/admin.php`'s whole group is already gated by the `admin` middleware (`EnsureUserIsAdmin`, Checkpoint 8), and every ability these two Policies expose is just `$user->isAdmin()` — an extra `$user->can()` call would be redundant, not defense in depth. Matches the existing convention in `Admin\VehicleController`/`CustomerController`, neither of which calls `$user->can()` either; the Sanctum controllers still need their own explicit checks since they have no equivalent middleware.
- **`available_transitions` is computed server-side in `AdminQueryService::orderDetail()`, not derived client-side from `order_status`.** `TransitionOrderStatus::allowedNextStatuses()` is the actual PHP source of truth for the transition table — duplicating that table (minus `order_placed`/`discarded`) into `orderFlow.ts` or a new frontend map would create a second place the two open product questions above could silently drift out of sync if the backend table ever changes. The frontend only turns each returned status string into a label/button via the existing `getVehicleStatusDisplay()` map (Checkpoint 5).
- **The route-name collision predicted in Checkpoint 10's decisions did hit `admin.orders.*` exactly as flagged** — `admin_tim_api_routes.php`'s pre-existing `orders.index` (Sanctum, `GET /admin/list/orders`) was renamed to `orders.list` before the new web `admin.orders.index` was added, confirmed via grep that nothing called the API route by name first (same verification Checkpoint 10 did for `vehicles.index`). `orders.by-user-type`/`orders.by-user` didn't need renaming — Checkpoint 11 has no web equivalent for either.
